# Android 팀원 검증 절차

## 이번 검증 결과

- Android Studio와 SDK 설치, Flutter Android 경로와 Java 21 설정을 완료했습니다. `flutter doctor -v`에서 문제가 없음을 확인했습니다.
- 개발 모드·출시 모드·진단 전용 APK를 모두 실제로 빌드했습니다.
- 정적 분석과 알림 데이터·친구 화면·함께 달리기 관련 테스트 10개가 통과했습니다.
- 실제 Android 기기는 이 환경에 없어 수신·화면 이동·수신 제어의 기기 검증은 팀원에게 인계합니다.
- Firebase 콘솔 접근이 거부되어 Crashlytics 활성화와 보고 도착 여부는 확인하지 못했습니다. 아래 절차로 팀원이 확인해야 합니다.
- 기존 Firebase·건강 데이터 플러그인의 Kotlin Gradle 플러그인 사용에 대한 향후 호환성 경고는 남아 있습니다. 현재 빌드는 성공했으며 추후 Flutter·플러그인 업그레이드 시 함께 확인합니다.

## 빌드 환경과 생성 방법

Android Studio, Android SDK 플랫폼 36·빌드 도구 36.0.0·NDK 28.2.13676358·플랫폼 도구와 Java 21을 설치했습니다. SDK는 `~/Library/Android/sdk`이며 Flutter의 Android SDK·Java 경로도 설정했습니다.

```sh
flutter doctor -v
scripts/build_android_qa.sh config/dev.json
```

빌드 스크립트는 설정 파일에서 모바일에 필요한 공개 항목만 추려 임시 파일로 사용하고 종료 시 제거합니다. 서버용 Gemini·공공데이터 API 키는 빌드 입력에서 제외합니다. 결과는 `build/qa/android/`에 세 APK와 `SHA256SUMS`로 저장합니다.

## 설치 파일

- `runspot-android-qa.apk`: 일반 앱의 개발용 설치 파일입니다. 푸시 수신과 화면 이동을 확인합니다.
- `runspot-android-release-qa.apk`: 일반 앱을 출시 모드로 빌드한 검증용 설치 파일입니다.
- `runspot-crashlytics-probe.apk`: `tool/crashlytics_probe.dart`로 빌드한 진단 전용 설치 파일입니다. 앱 실행 시 `runspot_diagnostics_probe`라는 고정된 비치명적 오류만 기록합니다. 실제 앱 충돌을 일으키지 않습니다. 일반 앱의 진입점에는 이 동작이 없습니다.

세 파일은 같은 앱 식별자와 개발용 서명을 사용하므로 동시에 설치하지 않습니다. 현재 프로젝트에 출시 서명 키가 없어 개발용 서명으로 검증합니다. 출시 스토어에 제출할 파일이 아닙니다. 기존 설치 앱의 서명이 다르면 덮어쓰기가 거부될 수 있습니다. 앱 삭제 시 기기에만 있는 러닝 기록이 지워지므로 미전송 기록을 먼저 확인해야 합니다.

## 푸시 수신

서로 다른 계정 두 개를 준비하고 이메일 인증·닉네임 등록을 완료합니다. 실제 다른 이용자에게 테스트 요청을 보내지 말고 팀원 간 합의한 계정만 사용합니다.

1. 테스트할 Android 기기에 일반 검증 APK를 설치합니다.
2. 로그인 후 설정 → 알림 설정 → 휴대폰 알림 켜기에서 권한을 허용합니다.
3. 친구 요청·함께 달리기 초대·내 글의 댓글/답글 수신 설정을 켭니다.
4. 상대 계정에서 친구 요청을 보낸 뒤 최대 약 1분 기다립니다. 친구 관계 수락 후 함께 달리기 초대도 확인합니다. 게시판의 테스트 글에 댓글을 달아 확인합니다.
5. 아래 표의 각 앱 상태에서 알림과 이동 화면을 기록합니다.

| 앱 상태 | 기대 동작 |
|---|---|
| 앱이 열린 상태 | 앱 안에 새 활동 안내가 나타나고 확인 버튼이 해당 화면으로 이동 |
| 홈 버튼으로 나간 상태 | 운영체제 알림이 도착하고 누르면 해당 화면으로 이동 |
| 최근 앱 화면에서 제거한 상태 | 제조사·배터리 정책에 따른 수신 여부를 기록하고 알림을 누르면 앱 시작 후 해당 화면으로 이동 |

Android 설정의 강제 종료는 일반적인 앱 종료와 다릅니다. 강제 종료 뒤에는 앱을 다시 열어야 수신이 재개될 수 있으므로 별도 사례로 기록합니다. 친구 요청은 소셜 요청 탭, 그룹 초대는 함께 달리기 화면, 댓글은 해당 게시글이 열려야 합니다. 잠금 화면에는 닉네임·댓글 본문·좌표가 표시되지 않아야 합니다.

## 수신 제어와 계정 변경

- 종류별 수신을 끈 뒤 새로 만든 활동은 푸시가 오지 않아야 합니다. 이미 휴대폰에 도착한 알림은 별도로 구분합니다.
- 양방향 차단 중에는 새 활동이 발송되지 않아야 합니다.
- 로그아웃한 기기로 이전 계정의 새 활동이 발송되지 않아야 합니다.
- 다른 계정으로 로그인한 뒤 이전 계정의 남은 알림을 눌러도 이전 계정의 내용이 열리지 않아야 합니다.
- 요청 취소·초대 만료·글 삭제 뒤 남은 알림을 눌러도 없는 내용을 정상 내용으로 표시하지 않아야 합니다.

## Crashlytics 연결

Crashlytics는 Firebase가 제공하는 앱 오류 수집 도구입니다. 테스트를 위해 서비스 계정 비밀이나 FCM 토큰을 팀원에게 전달할 필요가 없습니다.

1. Firebase 콘솔의 `capstone-running` 프로젝트에서 Crashlytics 화면을 열고 Android 앱 `com.runspot.runquest`를 선택합니다. 시작 안내가 나오면 콘솔에서 설정을 완료합니다.
2. `runspot-crashlytics-probe.apk`를 설치하고 네트워크가 연결된 상태에서 실행합니다.
3. 앱을 닫은 뒤 다시 실행합니다. 이전 실행의 보고서 전송을 확인하기 위한 절차입니다.
4. Firebase 콘솔에서 `runspot_diagnostics_probe` 이벤트가 보이는지 확인합니다. 반영까지 수 분이 걸릴 수 있습니다.
5. 오류 설명이 고정된 검증 문구인지 확인합니다. 좌표·이메일·인증 토큰·요청 본문·임의의 예외 원문이 없어야 합니다. Firebase의 기본 앱·기기 메타데이터는 포함될 수 있습니다.
6. 검증이 끝나면 일반 APK로 교체합니다. 진단 전용 APK를 실제 사용자에게 배포하지 않습니다.

진단 이벤트를 콘솔에서 확인해야 연결 검증이 완료됩니다. 빌드 성공이나 전송 API 호출만으로 보고 도착을 검증했다고 판단하지 않습니다.
